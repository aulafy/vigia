# Pushed inventory and WordPress

A hand-written inventory goes stale the day someone updates a plugin and forgets the JSON. After that, Vigía matches vulnerabilities against versions that no longer exist: it misses the new ones and alerts on ones already fixed. The fix is to let each server **report what it really runs**, every day, signed, and to alert when a server stops reporting.

```text
server (cron) ── vigia-collect.sh ── signed POST /api/inventory/<asset> ──▶ Vigía
   WP-CLI, lockfiles, SBOM,                                                 ├─ KEV / OSV / endoflife.date / Wordfence
   OS and runtime versions                                                  └─ no push within max age → P2
```

## What a server can report

`deploy/vigia-collect.sh` gathers any combination of these sources. It needs only `sh`, `openssl` and `curl`.

| Option | Source | Feeds |
|---|---|---|
| `--wp DIR` | WP-CLI: core version, plugins and themes, with their active or inactive status | Wordfence Intelligence, endoflife.date, KEV |
| `--npm FILE` | `package-lock.json` (v1–v3). Dev dependencies are skipped. | OSV |
| `--composer FILE` | `composer.lock`. `packages-dev` and `dev-*` branches are skipped. | OSV |
| `--cyclonedx FILE` | A CycloneDX JSON SBOM, for example from `syft` or `trivy`. Each component's purl is mapped to its OSV ecosystem, including Debian, Ubuntu and Alpine packages. | OSV |
| `--spdx FILE` | An SPDX JSON SBOM (purl external references) | OSV |
| `--os` | `/etc/os-release`: Ubuntu, Debian, RHEL, Rocky, AlmaLinux, Alpine… | endoflife.date |
| `--runtimes` | Versions of `php`, `node`, `nginx`, `apache`, `mysql`/`mariadb`, `postgresql`, `redis` and `openssl` found on the PATH | endoflife.date, KEV |

Each push **replaces** that asset's pushed components. The components declared by hand in `inventory.json` are kept and merged with them, so both can be used together.

## Setup

1. Set a random `CHECKIN_SECRET` on the Vigía server (`openssl rand -hex 32`). It is the same secret used for backup check-ins.
2. Make Vigía reachable over HTTPS from the servers (see [deployment.md](deployment.md#exposing-the-dashboard-optional)).
3. Copy `deploy/vigia-collect.sh` to each server, try it with `--dry-run`, then schedule it:

```bash
# WordPress site, daily at 03:15
15 3 * * * VIGIA_URL=https://vigia.example.com VIGIA_CHECKIN_SECRET=… WP_CLI="sudo -u www-data wp" \
  /usr/local/bin/vigia-collect.sh acme-shop --wp /var/www/html --os --runtimes

# Node + PHP app with an SBOM generated by syft
20 3 * * * syft dir:/srv/app -o cyclonedx-json > /tmp/sbom.json && \
  VIGIA_URL=… VIGIA_CHECKIN_SECRET=… /usr/local/bin/vigia-collect.sh acme-api --cyclonedx /tmp/sbom.json --os --runtimes
```

`WP_CLI` defaults to `wp`. Run WP-CLI as the web server user (`sudo -u www-data wp`), or use `wp --allow-root`. If PHP prints notices on standard output, the JSON breaks and Vigía answers `400`. Fix the notices or set `display_errors=Off` for the CLI.

### What happens on a push

- The response says what was recognised: `{"ok":true,"components":42,"wordpress":18,"packages":20,"eol":4,"errors":[]}`. Parts it cannot read are listed in `errors` and do not block the rest.
- OSV, Wordfence, end-of-life and freshness checks run right away instead of waiting for their next cycle.
- **The first push of an asset counts as onboarding:** hundreds of findings arrive as one summary per source, while P1s still ring.
- When a later push shows an upgraded version, the alerts it fixes close on their own. A fixed P1 sends a RECOVERED message.

### Freshness

Once an asset has pushed, Vigía expects a new push every **48 hours**. A late push raises a P2 "inventory out of date", because matching may be running on old versions. Set `"inventoryMaxAgeHours": 24` on the asset to choose the window, or to expect pushes from an asset that has never reported. That way a collector that was never installed is noticed too.

### Protocol

```text
POST /api/inventory/<assetId>
x-vigia-timestamp / x-vigia-signature: same scheme as backup check-ins (docs/backups.md#check-in-protocol)

{"host": "web1", "parts": [
  {"kind": "wp", "core": "6.4.3", "plugins": [{"name": "contact-form-7", "status": "active", "version": "5.9"}], "themes": [...]},
  {"kind": "npm-lock", "lock": { …package-lock.json… }},
  {"kind": "composer-lock", "lock": { …composer.lock… }},
  {"kind": "cyclonedx", "bom": { …CycloneDX… }},
  {"kind": "spdx", "doc": { …SPDX… }},
  {"kind": "os", "id": "ubuntu", "version": "22.04"},
  {"kind": "runtime", "name": "php", "version": "8.1.27"}
]}
```

The body may be up to 16 MB, with up to 20,000 components per asset. Responses: `200`, `400` (invalid JSON or nothing recognised), `401` (signature), `404` (unknown asset), `409` (replay).

## WordPress vulnerabilities (Wordfence Intelligence)

OSV covers WordPress plugins poorly. Vigía uses the **Wordfence Intelligence v3** feed instead: tens of thousands of vulnerabilities in WordPress core, plugins and themes, with exact affected version ranges. It is free for personal and commercial use with an API key.

1. Create a free account and get an API key at <https://www.wordfence.com/products/wordfence-intelligence/>.
2. Set `WORDFENCE_API_KEY` in `.env`.

Vigía downloads the production feed every `WORDFENCE_HOURS` (default 6), keeps a compact index in `data/wordfence.json`, and matches every 30 minutes. If a download fails, it keeps using the cached copy for up to 24 hours. Past that, the feed counts as stale and you get a P2.

WordPress components come from `--wp` pushes, or can be declared by hand in the stack:

```json
{ "wp": "core", "version": "6.4.3" },
{ "wp": "plugin", "slug": "contact-form-7", "version": "5.9" },
{ "wp": "theme", "slug": "astra", "version": "4.6.0" }
```

`slug` is the directory name in `wp-content/plugins/` or `wp-content/themes/`, which is also the `name` that WP-CLI prints.

| Finding | Priority |
|---|---|
| CVE in CISA KEV, or CVSS ≥ 9 on a high-criticality asset, or CVSS ≥ 9 and **unauthenticated** | P1 |
| CVSS ≥ 7 | P2 |
| Lower or unscored | P3 |

The alert says whether a fix exists and which version to update to: "Fix: update to 5.3.2", or "No fix available: remove or replace it". **Inactive plugins are included on purpose.** Their files can still be reached and exploited while they are installed, so the alert marks them as "inactive".

Records marked as informational in the feed are skipped. Alerts cite *Wordfence Intelligence* as the source, and Vigía uses the data under Wordfence's terms. See the copyright notices included in the feed.
